## 4.X Software Architecture

The test software architecture is designed to ensure modularity, traceability, and reproducibility of signal acquisition, processing, and performance metrics used for verification testing. The architecture follows a message-based publish/subscribe paradigm, implemented using a Real-Time Messaging Architecture (RTMA), to decouple data acquisition, signal processing, metric computation, logging, and visualization.

---

## 4.X.1 Architectural Overview

The software system is composed of independent processing modules that communicate exclusively through typed messages transmitted over an RTMA message bus. Each module performs a single, well-defined function and publishes its outputs as time-stamped messages that may be consumed by one or more downstream modules.

This design enables:

- Deterministic signal processing
- Independent verification of individual software components
- Reproducible data logging for post-hoc analysis
- Separation of safety-critical computation from visualization and user interface elements

A high-level data flow is shown below:

Accelerometer Acquisition  
↓ AccelMsg  
Digital Signal Filtering  
↓ FilteredAccelMsg  
Frequency Estimation  
↓ FrequencyMsg  
Signal-to-Noise Ratio Estimation  
↓ SNRMsg  
Reference Frequency Input  
↓ ReferenceFreqMsg  
Frequency Error Computation  
↓ FrequencyErrorMsg  
Data Logging and Visualization

---

## 4.X.2 Signal Acquisition and Conditioning

Raw tri-axial accelerometer samples are acquired from the test device via serial communication and published as AccelMsg messages. These messages contain a timestamp and raw acceleration values and represent the earliest digital representation of sensor data.

A digital filtering module subscribes to AccelMsg messages and applies band-limited filtering consistent with the clinically relevant HFOV frequency range (5–15 Hz). The filtered signal is published as FilteredAccelMsg, which serves as the standardized input for all downstream metric computations.

---

## 4.X.3 Metric Computation Modules

Frequency and signal quality metrics are computed in independent software modules to ensure traceability and isolation of verification logic.

### Frequency Estimation Module

Subscribes to FilteredAccelMsg and estimates oscillation frequency using frequency-domain and time-domain methods. The resulting estimate is published as a FrequencyMsg.

### Signal-to-Noise Ratio (SNR) Estimation Module

Subscribes to FilteredAccelMsg and computes signal-to-noise ratio (SNR) in decibels (dB) using power spectral density–based methods consistent with the acceptance criteria defined in Section 2.2. The result is published as an SNRMsg.

### Frequency Error Computation Module

Subscribes to both FrequencyMsg and ReferenceFreqMsg messages. The absolute frequency error is computed as:

Frequency Error = | f_device − f_reference |

The result is published as a FrequencyErrorMsg and used to assess compliance with the frequency accuracy acceptance criterion defined in Section 2.1.

---

## 4.X.4 Reference Frequency Input

The reference oscillation frequency generated by the benchtop simulation is introduced into the software system as a ReferenceFreqMsg. This value is treated as ground truth for verification testing and is logged alongside measured device outputs to enable direct comparison during post-processing analysis.

---

## 4.X.5 Data Logging and Traceability

All verification-relevant messages, including frequency estimates, SNR measurements, reference frequency, and frequency error, are subscribed to by dedicated logging modules. Logged data are stored in time-stamped, structured files suitable for import into Python-based data analysis tools (e.g., pandas).

This approach ensures:

- Complete traceability of verification results
- Reproducibility of analysis
- Separation of data capture from real-time visualization

---

## 4.X.6 Visualization and User Interface

Graphical user interfaces and dashboards subscribe to RTMA messages but do not participate in metric computation. This ensures that visualization components do not influence verification outcomes and may be modified or replaced without affecting test validity.

---

## 4.X.7 Software Verification Rationale

The modular RTMA-based architecture supports verification testing by:

- Allowing independent validation of signal processing and metric computation modules
- Enabling offline replay of recorded test data
- Supporting statistical analysis of performance metrics over extended test durations
- Maintaining clear separation between safety-critical computation and non-critical display logic
